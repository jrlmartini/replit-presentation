# Conatus Presentation System — README

Sistema de geração de apresentações da Conatus Ambiental com **design system + templates + regras de agente + validação estruturada**, com saída principal em **web deck (link compartilhável)**.

Este repositório foi pensado para permitir que um app (ex.: no Replit) gere apresentações a partir de briefing/prompt, mantendo consistência visual, narrativa e editorial.

---

## 1) Objetivo do sistema

Gerar apresentações padronizadas da Conatus com:
- **templates de slides definidos**
- **regras claras para o agente (LLM)**
- **schema/validator para garantir consistência**
- **renderização web (viewer)**
- opção futura de **export (PDF/PPTX)**

---

## 2) Filosofia de arquitetura (importante)

Este sistema **não depende apenas de prompt**.

Ele combina 3 camadas:

### A. Regras semânticas (LLM-friendly)
Arquivos `.md` que orientam comportamento, estilo e seleção de slides.

### B. Regras estruturais (machine-enforced)
Schemas + validators (ex.: Zod) que impedem saídas inválidas.

### C. Regras de composição (template registry)
Definem **quais componentes** podem existir em cada tipo de slide.

> **Resumo:** o LLM sugere e compõe conteúdo; o sistema valida e renderiza.

---

## 3) Arquivos principais de regras (MD)

### `PRESENTATION_AGENT_RULES.md`
Constituição geral do agente:
- pode / não pode
- tom de voz padrão
- confidencialidade
- uso de placeholders
- regras globais de conteúdo
- comportamento com briefing incompleto

### `SLIDE_SELECTION_GUIDE.md`
Guia de escolha de templates:
- quando usar cada slide type
- padrões de sequência narrativa
- critérios light vs dark
- anti-padrões de seleção

### `CONTENT_STYLE_GUIDE.md`
Guia editorial:
- estilo de títulos
- bullets
- subtítulos
- texto de gráfico
- linguagem PT-BR
- ajuste de tom por público

---

## 4) Ordem de precedência das regras (obrigatório)

Se houver conflito entre regras, seguir esta ordem:

1. **Schema + Validator** (máquina)
2. **Template / Component Registry**
3. **PRESENTATION_AGENT_RULES.md**
4. **SLIDE_SELECTION_GUIDE.md**
5. **CONTENT_STYLE_GUIDE.md**
6. Preferências estéticas/contextuais

> O agente **não deve** quebrar schema/registry para atender preferência textual.

## 6) Como o pipeline funciona (Planner → Composer → Validator → Viewer)

## 6.1 Entrada
O usuário fornece um **briefing híbrido**:
- campos estruturados (tipo de deck, público, objetivo, nº de slides etc.)
- observações em texto livre
- assets opcionais (imagens, logos)
- dados pontuais (quando houver gráfico)

### Exemplo (conceitual)
`briefing.json` → objetivo, público, estrutura desejada, restrições, senha etc.

---

## 6.2 Planner (LLM)
Responsável por:
- organizar a narrativa
- definir sequência de slides
- escolher slide types oficiais
- sugerir agenda/separadores

### O Planner deve usar
- `PRESENTATION_AGENT_RULES.md`
- `SLIDE_SELECTION_GUIDE.md`

### O Planner não deve fazer
- layout pixel-perfect
- criar templates novos
- inventar dados

### Saída esperada
`deck_plan.json` (estrutura narrativa do deck)

---

## 6.3 Composer (LLM)
Responsável por:
- preencher conteúdo de cada slide
- gerar títulos, subtítulos, bullets, textos
- posicionar conteúdo em componentes válidos (AST/schema)
- usar placeholders quando faltar dado

### O Composer deve usar
- `PRESENTATION_AGENT_RULES.md`
- `SLIDE_SELECTION_GUIDE.md`
- `CONTENT_STYLE_GUIDE.md`

### O Composer não deve fazer
- extrapolar dados
- criar campos fora do schema
- usar componentes não permitidos para o slide type

### Saída esperada
`deck_ast.json` (deck estruturado e renderizável)

---

## 6.4 Validator (determinístico, sem depender do LLM)
Responsável por:
- validar schema
- validar slide types permitidos
- validar componentes por slide type
- checar limites de texto
- bloquear saídas inválidas

### Exemplo de validações
- `slide.type` permitido?
- `chart_text` tem gráfico + texto explicativo?
- `title` excede limite?
- `variant` compatível?
- `chart_block` sem dados?

### Resultado
- **Aprovado** → segue para renderização
- **Reprovado** → retorna erro estruturado (idealmente com motivo + campo afetado)

---

## 6.5 Viewer / Renderer (web)
Responsável por:
- renderizar `deck_ast.json`
- aplicar tema Conatus
- aplicar templates e componentes
- exibir deck com transições leves
- proteger acesso por senha

### Recomendação (MVP)
- **React + Reveal.js + Tailwind**
- viewer em rota tipo `/deck/:id`

---

## 7) Papel de cada tipo de regra no sistema (resumo prático)

| Camada | Função | Exemplo |
|---|---|---|
| Markdown rules | comportamento e estilo | “Não inventar dados” |
| Schema | estrutura válida | `slide.type` enum |
| Registry | composição por template | `light_chart_text` aceita `chart_block` + `text_block` |
| Validator | enforcement | barrar excesso/ausência de campos |
| Viewer | renderização | HTML/CSS/JS do slide |

> Os arquivos `.md` **orientam**, mas quem **garante** é schema + registry + validator.
